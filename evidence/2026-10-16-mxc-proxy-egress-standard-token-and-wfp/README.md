# MXC with `runtimeConfig.networkProxy` at a loopback proxy, from a standard token and with the Windows Filtering Platform captured during launches, 2026-10-16

Two launchers, Windows 26200.9711, three runs per arm in each of two batches: a standard (non-elevated) token, and an elevated token with `netsh wfp` captures before, during and after every launch. Both repeat the policy of `evidence/2026-10-15-mxc-proxy-egress/`.

## Questions

1. **Standard token.** With the policy of the 2026-10-15 record (`runtimeConfig.networkProxy` `http://127.0.0.1:18110`, no `allowedProxyPeer`, `network.ingress.default` allow, `network.ingress.hostLoopback` allow, `network.egress.default` deny, no egress rules), launched from a non-elevated Medium-integrity token: does the launcher accept the policy, and is every direct (non-proxy) connect from inside the container refused while a request through the proxy works?
2. **WFP capture.** During a launch under the same policy, does the Windows Filtering Platform (WFP) hold filters that reference the container's AppContainer SID, or is the block capability-only, as the 2026-10-15 record's MXC log lines (`firewall_rules_created` 0) could be read to suggest?

## Result in one paragraph

**Standard token (`runs/run-20261016-1/`).** Both launchers accepted the policy at `--dry-run` 3 of 3 and launched it 3 of 3 (exit code 0). A request through the configured proxy to a second loopback listener succeeded in every case (9 of 9 requests per arm, seen by the container, by the proxy log and by the listener log). A direct connect to that listener, a connect to the default gateway (port 80) and a connect to 1.1.1.1:443 were each refused with Windows error 10013 in 3 of 3 runs per arm, and the listener logged no direct hit. From an unconfined process on the same account the same destinations connected before and after every launch. The harness verdict, from fixed rules written before the runs, is HOLD for both arms. **WFP capture (`runs/run-20261016-2/`).** Same policy, elevated token. Egress was HOLD 3 of 3 per arm again. In all six captured launches eight filters existed during the launch that existed neither before nor after it (filter count 1008 before, 1016 during, 1008 after, identical key sets before and after). Four are named "Tessera Sandbox Filter" (provider "Tessera Sandbox Provider", a component of Windows and not of MXC): per launch, at `ALE_AUTH_CONNECT` for IPv4 and IPv6, a PERMIT for TCP to 127.0.0.1 (IPv6: ::1) port 18110, the configured proxy port, and a BLOCK with no address, port or protocol condition, all keyed to that run's AppContainer SID. Four are Windows Firewall service loopback PERMITs at `ALE_AUTH_RECV_ACCEPT` (two named `Sandbox.{GUID}`, two named "MXC-Loopback"). So the block is not capability-only. **Which layer produced WinError 10013 for any attempt is not isolated by either batch**, and the positive control built to prove the capture could see an added filter produced nothing and proves nothing either way. This is a finding about these two launchers, with this policy, on this build, on one machine; it is not a claim that MXC is secure.

## Method

As the 2026-10-15 record: every run is a separate launcher invocation preceded by `--dry-run`; inside the container B2 (three HTTP requests through a stdlib forwarding proxy on 127.0.0.1:18110 to a second loopback listener on 127.0.0.1:18111, which must show in the container report, the proxy log and the listener log), B3 (one direct connect to the second listener), B4(i) (one connect to the default gateway, port 80) and B4(ii) (one connect to 1.1.1.1:443); controls B5 from an unconfined process on the same account, once per batch (`control-b5.json`) and again around every launch (`unfenced_pre`, `unfenced_post`). Only Windows error 10013 counts as a refusal; a timeout or any other error blinds the run. Before and after every run the harness snapshots ACL hashes of the granted folders, sandbox registry mappings, the firewall rules whose program is either interpreter, the firewall profiles, the loopback-exemption list and the WinHTTP proxy; any difference stops the batch.

Changes in the harness since 2026-10-15 that bear on these records: a launch failure that is not an MXC policy-validation refusal (a JSON envelope with code `policy_validation`) reads INSTRUMENT-BLIND and not REFUSED; a missing or non-AppContainer container token or an empty direct-attempt report also reads INSTRUMENT-BLIND; the container's own token is recorded (`payload.token`); AppContainer-mapping changes are compared by SID and name; `--token standard` requires a non-elevated Medium-integrity launching token and records the token in every record. For the WFP batch, `--wfp-capture` (elevated only) adds the three captures, an analysis of the filters that appeared during the launch and that reference the run's AppContainer SID, a batch summary that carries the header's list of fields unreadable under the token and counts a run record without `state_changed_by_run` as unknown (`state_unknown_runs`; the standard-token batch's harness predates this, and its 6 records all carry `state_changed_by_run`), and a positive control: a Windows Firewall rule for a synthetic package SID, created and removed, to check that the capture can see an added filter.

An independent reviewer re-read each batch after it ran. For the WFP batch the reviewer parsed the raw XML with their own parser (keyed by `filterKey`, not the probe's `summarise.py`), read MXC's source at `525d0f25`, and searched the bytes of MXC's binaries and of System32.

### The eight filters that existed only during each launch (WFP batch, identical shape in both arms, all 6 launches)

Filter keys differ per run; before-and-after key sets are identical. In the files the keys are placeholders (`GUID-nnnn`), numbered consistently inside `runs/run-20261016-2/`; the provider and sublayer keys below are fixed values and are kept.

| Filters | Layer | Action | Keyed to | Notes |
|---|---|---|---|---|
| 4 named "Tessera Sandbox Filter" | `ALE_AUTH_CONNECT` v4 and v6 (one PERMIT and one BLOCK each) | PERMIT, BLOCK | `FWPM_CONDITION_ALE_PACKAGE_ID` equal to that run's AppContainer SID (the SID read back from inside the container) | provider "Tessera Sandbox Provider" `{2f8c6d14-3b7e-4a59-9c08-1d4e7a6b2f30}`, sublayer "Tessera Sandbox SubLayer" `{7b1e9a2c-9d4f-4c8a-b321-5e6d2f8a1c44}` (weight 65533). The PERMIT is TCP to 127.0.0.1 (v6: ::1) port 18110, weight 8; the BLOCK has no address, port or protocol condition, weight 1, so it blocks every other outbound connect from the package. Each of the four also carries an `FWPM_CONDITION_ALE_USER_ID` condition, a security descriptor naming the launching account (its SID is redacted in these files), so a filter matches a connect made by that package under that account. Whether a connect made on the container's behalf by a process running as another identity is covered by them was not tested |
| 2 named `Sandbox.{GUID}` | `ALE_AUTH_RECV_ACCEPT` v4 and v6 | PERMIT (inbound loopback) | the run's package SID | Windows Firewall service app-isolation sublayer; they carry the SID of MXC's named loopback peer in a remote-user security descriptor |
| 2 named "MXC-Loopback" | `ALE_AUTH_RECV_ACCEPT` v4 and v6 | PERMIT (inbound loopback) | a constant package SID `S-1-15-2-2397545170-...` (the same in all six runs, absent outside the launch); the run SID appears only inside a remote-user security descriptor | see ownership below |

Six of the eight are keyed to the run's own package; two (the "MXC-Loopback" pair) only mention the run SID. The probe's own summary lists all eight as "referencing the container SID"; that overstates two of them (its substring match counts a mention in a security descriptor), and the re-count below separates them.

**Ownership.** The four Tessera filters are Windows' and not MXC's: the string "Tessera Sandbox" is in System32 `processmodel.dll` and absent from every exe and dll in both MXC builds' directories; MXC 525d0f25 `docs/logging-access-denied.md:260-264` calls Tessera an internal Windows component, `:279-280` names these two keys, and `:248` states "MXC does not coordinate with WFP directly"; `base_container_helpers.rs:94-97` states that proxy mode deliberately omits the internet capability. The constant package SID is the AppContainer SID derived from the name `MXC-Loopback` (SHA-256 of the lower-cased UTF-16LE name, first 28 bytes read as seven little-endian 32-bit values; the derivation reproduces all seven sub-authorities, and the same computation on a Store package name reproduces that package's SID in the run records' AppContainer mappings). `MXC-Loopback` is MXC's own identifier: `base_container_helpers.rs:24` defines `LOOPBACK_NETWORK_PEER` as "MXC-Loopback" (used at `:176` and `base_container_runner.rs:3231,3441`), `docs/backends/process-container/networking.md:121-124` says that in proxy mode the host-loopback setting "selects both the `networkLoopback` capability and the `MXC-Loopback` peer", and the ASCII string is in MXC's `wxc-exec.exe` and `mxc_ffi.dll`. The four app-isolation filters (the two `Sandbox.{GUID}` filters and the two "MXC-Loopback" filters) are one reciprocal loopback peering between the run container and MXC's named peer, installed by the Windows Firewall service (provider `FWPM_PROVIDER_MPSSVC_APP_ISOLATION`), not by MXC code. That MXC requests the peer through its process security environment spec is MXC's source's statement and was not observed here. This is consistent with `firewall_rules_created` 0 in every launch (MXC-authored Windows Firewall rules only) and inconsistent with a capability-only account of the block.

**Which layer gave 10013.** B3 (second loopback listener, port 18111) is attributable to the Tessera BLOCK by inference from the filter shape, not observed: B2 to the same address on port 18110 succeeded, and the only run-keyed filters with a port condition are the two Tessera PERMITs for 18110. B4(i) (gateway) and B4(ii) (1.1.1.1:443) are not distinguishable: there are at least two candidates, the missing network capability and the Tessera BLOCK, and each would refuse. The dumps also hold 728 filters of Bitdefender's own providers (520 "Bitdefender IGNIS Provider", 208 "Bitdefender BDDCI4 Provider", in the before-launch dump of the first run) which were present and not analysed, so a third source is not excluded. No WFP net-event capture and no `captureDenials` reason codes were recorded, so no refusal is tied to a filter.

**Positive control: uninformative.** The synthetic-package-SID rule produced no filter the analysis found (`wfp/control-present-filters.xml` is byte-identical to the first run's before-launch dump, `wfp/A-A1-r1-075819-before-filters.xml`; so is `control-removed-filters.xml`) and was removed and verified absent (`wfp-control.json`: created true, removed_verified true, absent_after_removal true, ok false). It tests how the Windows Firewall service treats a package that no AppContainer registered, not the capture's sight. The capture's sight rests on the runs themselves (eight per-launch filters with exact-SID conditions, clean before and after). The failure neither weakens nor strengthens the FILTERS-PRESENT reading; attribution is not answered.

## What the counts are

Two repeats of three on one machine: 37 seconds apart in the standard-token batch and 84 seconds in the WFP batch. They are not a distribution. The B2 control passing (all three logs agree, 9 of 9 per arm) is what lets a B3 refusal be read as the container boundary and not a dead listener. The standard-token batch answers its question as stated: HOLD under a standard token, for these two builds, on this host, TCP only, with this policy. It is a repeat under a different token, **not a measurement of a token effect**: the token, all four harness files, `launch.ps1`, a new `launch-standard.cmd` and the Bitdefender process set (1 and 14 processes in the 2026-10-15 batches, 16 here) changed together, while the launcher hashes and the Windows build did not; the WFP state could not be read without elevation. Because the unconfined controls ran from a different interpreter path (same hash) than the container, this batch alone does not attribute the refusal to MXC (a per-program rule of a third-party firewall on the container's path would also produce 10013); the 2026-10-15 batch with Bitdefender uninstalled gave the same 10013 pattern. In the WFP batch the filter shape is the same in all six launches, so existence and ownership of the eight filters are well supported; the mechanism behind any single refusal is not measured.

## Not measured

The WFP filter state under a standard token (unreadable without elevation), including whether any filter appeared during a launch from that token (the WFP batch ran elevated); which filter or layer produced WinError 10013 for any attempt, and whether removing the internet-capability omission alone, or the Tessera filters alone, would still hold; whether the Windows Firewall service installs the MXC-Loopback peering in response to MXC's request, as the source implies, or on another trigger (not observed); whether Tessera is a documented public Windows interface (MXC calls it internal); an isolated token effect; whether a per-program Bitdefender rule on the container's interpreter path contributed; UDP, ICMP or DNS egress; IPv6 behaviour (v6 filters exist, but no v6 connect was tried); HTTPS or CONNECT through the proxy; destination ports other than 80, 443, 18110 and 18111; an identity-scoped proxy (`allowedProxyPeer`); the session-isolation backend; host-to-container ingress; nono under MXC; any build other than the two run, or any Windows build other than 26200.9711; variance beyond three runs per arm per batch; Bitdefender's own firewall rules and logs. Other open items for the probe, recorded after the WFP batch: its substring match overcounts the filters that reference the container SID (six are keyed to it and two mention it), and the positive control should be replaced by one that uses a registered package or a raw WFP filter. The console capture of the standard-token batch is incomplete (the runner returned early); these records are read from the raw run records, not from the console.

## How to re-run

As the 2026-10-15 record (`evidence/2026-10-15-mxc-proxy-egress/`): Windows with the two `wxc-exec` launchers and a Python for the container. The standard-token batch needs a non-elevated Medium-integrity launching token (`launch.ps1 -Token standard`, or `launch-standard.cmd`; both re-check the token); the WFP batch needs an elevated console and `--wfp-capture`. The launcher script checks the probe files against an approved list you write yourself (`<sha256>  <filename>` per line in `APPROVED_SHA256.txt`); the paths in `run_probe.py` are constants at its top. `python -I -B self_test.py` runs without MXC but binds the live probe ports 127.0.0.1:18110, 18111 and 18113: never run it while a live run may be in progress or pending, and never alongside another MXC self-test on the same machine. A live run creates and removes per-container ACL grants and may leave state if interrupted. Run it on a machine you can afford to change.

The probe copies here are the files that ran (their `README.md` and `self_test.py` as committed). Later changes in the private repository are not in them.
